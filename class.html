Communication cost

When many computers work together, the slow part is moving data between them, not doing the maths.

  • A cluster has hundreds of processors. They are cheap, and many sit idle. Doing more calculations is rarely the problem.
  • The network that links the machines is shared and slow. Moving data is the expensive part.
  • So we judge a job by how many bytes travel across the network, not by how much arithmetic it does.
  • Simple rule: the cost of a step is about the size of the data it reads. The whole job's cost is all of those added together.

Example

Counting short DNA chunks (k-mers): 1 billion reads, each giving 100 chunks, is 100 billion tiny "(chunk, 1)" messages. If every one crosses the network, that is a mountain of traffic. A combiner adds up the chunks on each machine first, so only a few totals travel instead of billions of ones. Same answer, a tiny fraction of the traffic.

Use case

When a genomics job is slow, the real fix is almost always to make the machines send less data to each other (add a combiner, pick a smarter key), not to buy faster processors.

The parallelism trade-off

You can spread work over more machines to go faster, but that makes them send more data to each other. You cannot have both.

Every MapReduce job is described by two numbers:

  • Reducer size (q): the most data any single machine has to hold and process at once. A small q means a light load per machine, so you can use many machines in parallel.
  • Replication rate (r): how many copies of each input piece get sent out. A big r means lots of copies travelling, which is more network cost.
The trade-off
  • Want more machines working at once (small q)? Then each piece of data must be sent to more of them, so r goes up.
  • Want to send less data (small r)? Then fewer machines share the work, so q goes up.
  • You always pay for parallelism with data movement.

Example

Comparing every read with every other read (needed to assemble a genome). Put it all on one machine: nothing is copied (small r), but that machine must hold everything (huge q, impossible). Split it across many machines: the load per machine drops (small q), but each read must be copied into many groups (big r, huge network cost). Both extremes hurt.

Use case

This is why real assembly tools never compare all reads directly. They first group reads by a shared chunk, and only compare reads inside the same group. They redesign the problem so the expensive step never happens. Tools like minimap2 and Kraken are built on this trick.

The genomic data problem

Modern biology produces enormous amounts of data, and ordinary tools cannot keep up.

~200 GB
raw data from sequencing one human genome
$100M → <$1000
cost to sequence a genome, in 2001 and now
>50 PB
size of the public NCBI read archive, still growing

That scale creates five very practical challenges. The rest of Unit II is a set of answers to them:

  • Volume: one study can be hundreds of terabytes. No single hard drive holds it.
  • Finding things: a genome is 3 billion letters. Locating one gene or one mutation needs smart searching.
  • Trust: which exact version of the data produced this result, and who changed it?
  • Moving it: sending terabytes between labs across the world is slow.
  • Computing: analysis must run on many machines at once to finish in reasonable time.

Why it matters

Sequencing got cheap faster than computers got powerful. The data now grows faster than the machines that process it, so these problems get harder every year, not easier.

Annotations and search

Raw DNA is just letters. Annotations are notes that say what the letters mean, stored so you can find any one instantly.

What an annotation is
  • A label attached to a position on the genome.
  • For example: "this stretch is the BRCA1 gene", "this single letter is a known disease mutation", "this region switches a gene on and off".
Why raw sequence is not enough
  • Knowing a patient has a T where most people have a C means nothing on its own.
  • You need to know: is it inside a gene? Is it a known disease variant? Is it rare or common?
  • Those answers live in annotation databases, not in the DNA itself.
Stored so it can be searched
  • Annotations sit in indexed databases, so a lookup like "what is at chromosome 17, position 43,044,295?" returns instantly.
  • Without an index, every question would mean reading the whole genome again.
  • Common databases: Ensembl and UCSC (genes), dbSNP (known variants), ClinVar (variants linked to disease), gnomAD (how common a variant is).
  • Common file formats: GFF and GTF (genes), BED (regions), VCF (variants).

Example

Question: "list every known harmful mutation inside the BRCA1 gene" (this gene affects breast-cancer risk). Steps: find where BRCA1 sits, pull all variants in that range, keep the ones marked harmful.

BRCA1  is at  chr17: 43,044,295 - 43,125,483
→ get all variants in that range      (dbSNP)
→ keep those marked "pathogenic"       (ClinVar)

With indexed storage this takes seconds. On plain files it would be three full scans of the genome.

Use case

A clinical lab receives a patient's genome and must report which of their variants are known to cause disease. That report is only possible because annotations are stored in a fast, searchable form.

Tracing data with iRODS

In science and medicine you must prove where data came from and be able to reproduce old results. iRODS is software that keeps this history for you.

The problem
  • A result is produced today from some dataset.
  • Two years later someone asks: which exact version of the data was used? Who processed it? Has it changed since?
  • If you cannot answer, the result cannot be trusted or repeated.
What iRODS is and gives you
  • iRODS stands for the integrated Rule-Oriented Data System. It sits on top of your storage and manages the data, not just holds it.
  • Provenance: a record of where each dataset came from and every step done to it.
  • Versioning: old versions are kept, so a past analysis can be reproduced exactly.
  • One unified view of data spread across many servers and locations.
  • Automatic rules, for example "always keep three copies" or "tag every file with its study name".

Use case

A hospital lab reports a patient's variant result. Years later an audit asks how it was produced. Because iRODS tracked the data version, the reference used, and every processing step, the lab can reproduce the exact result and prove it was correct.

Moving huge files

Genomic files are enormous, and ordinary internet transfer is far too slow. Special methods fix this.

The problem
  • You need to send 50 TB of sequencing data to a collaborator overseas.
  • Over a normal 1 Gbps link at full speed, that is about 5 days, and in practice longer.
Why normal transfer is slow
  • FTP and HTTPS use TCP, which slows down whenever the network is busy or drops a packet.
  • Over long distances, TCP cannot keep the connection full, so a fast link is mostly wasted.
  • The bottleneck is the method, not the bandwidth you are paying for.
Two faster methods
  • FASP (Aspera): the "Fast And Secure Protocol". It sends data over UDP and controls speed itself, so distance and packet loss stop slowing it down. It fills the whole link, turning a multi-day transfer into hours. Big archives like the EBI and NCBI offer it for downloads.
  • Torrents and seeding: the file is split into pieces held by many machines (seeders). A downloader grabs different pieces from different seeders at once. The more places that already have the data, the faster everyone else gets it.
MethodBest whenWhy
FTP / HTTPSSmall files, short distancesSimple and universal, but slow over long links.
FASP (Aspera)One big transfer, far awayUses the full bandwidth; distance and loss do not slow it.
TorrentPopular data, many recipientsThe load is shared across many seeders at once.

Use case

A reference dataset like the 1000 Genomes Project is wanted by thousands of labs. Sharing it by torrent spreads the load, so no single server is overwhelmed and everyone downloads faster.

Splitting the work

Genomic analysis breaks naturally into independent pieces, which is exactly what makes it easy to run on many machines at once.

Why it fits so well
  • Millions of reads can each be processed on their own. One read never needs another.
  • The genome can be split into regions, and each region handled separately.
  • Independent pieces are exactly what a cluster handles best.
The key move (same as Unit I)
  • The data (reads plus the reference genome) is large. Your program is small.
  • So you do not bring the data to the program. You send the small program to the machines that already hold the data.
  • What splits well: read alignment, k-mer counting, variant calling by region, and quality filtering.

Example

Aligning a billion reads on one computer could take weeks. Split across a 100-machine cluster, each machine aligns its own share, and the whole job finishes in hours.

Hadoop tools for genomics

Ready-made tools apply the Unit I machinery (Hadoop and Spark) to real genomic analysis, so you do not build it yourself.

How MapReduce fits an alignment job
map(read):     align the read, label it with its genome region
shuffle:       gather all reads that landed in the same region
reduce(region): call the variants in that region

That is map, shuffle, reduce, running on a genome, exactly the pattern from Unit I.

Real tools built this way
ToolWhat it does
CrossbowRead alignment and variant calling on Hadoop, for whole genomes.
CloudBurstParallel read mapping using MapReduce.
GATK on SparkThe standard variant-calling toolkit, parallelised with Spark.
HailAnalysis of very large variant datasets on Spark, used by gnomAD.
Why it pays off
  • A job that would take weeks on one machine finishes in hours across a cluster.
  • If a machine dies mid-run, only its part is redone, because the data is copied on other machines.
  • The same pipeline runs on 10 machines or 10,000 without being rewritten.

Honest limit

For a small dataset, one machine is faster, because a cluster adds coordination overhead. Reach for the cluster only when the data is genuinely too big to finish any other way.

RNA-seq and gene activity

DNA is the fixed recipe book. RNA-seq measures which recipes a cell is actually using right now.

What it measures
  • Not the DNA sequence, but gene activity: how strongly each gene is switched on.
  • That activity differs between a healthy cell and a tumour, or before and after a drug.
  • So RNA-seq shows what a genome is doing, not just what it contains.
The pipeline
reads  →  align to the genome  →  count reads per gene  →  expression table
  • Sequence the RNA in a sample, giving reads (just like DNA sequencing).
  • Align each read to find which gene it came from.
  • Count the reads for each gene. That count is how active the gene was.
  • That counting step is the same k-mer counting job from Unit I, with the gene as the key.
The gene expression table

The result is a big table: one row per gene, one column per sample, each cell a count.

            Sample A    Sample B    Sample C
  BRCA1        812         790          45
  TP53        1204        1190         160
  MYC          330         340        2100

Reading across: BRCA1 is busy in samples A and B, but almost silent in C. MYC is the opposite.

What you find in it
  • Differential expression: genes that change between two groups, such as tumour versus normal.
  • Clustering: samples that behave alike, which can reveal subtypes of a disease.
  • Biomarker discovery: a small set of genes whose activity predicts an outcome.

Example

Compare tumour samples with healthy ones, and look for genes that are far more active in the tumour. Those genes are candidates to study further, or to target with a drug.

Use case

At population scale this table is huge, with tens of thousands of genes across thousands of samples. That is why it is analysed with the distributed tools from this unit, such as Hail.
